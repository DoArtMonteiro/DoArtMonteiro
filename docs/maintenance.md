# Maintenance and recovery

## Refresh cadence

| Component | Source | Current cadence | Stale behaviour |
|---|---|---|---|
| Public contribution calendar | GitHub GraphQL `contributionsCollection.contributionCalendar`, without restricted-contribution fields or `read:user` | Daily at 05:17 UTC, after relevant source changes on `main`, or by manual dispatch | The image and `portfolio-assets/current.json` show the data-through date. The README workflow badge reports the latest run; mark the data stale after 36 hours without a successful refresh. |
| Selected-repository commit calendar | GitHub REST list-commits endpoint for the eight exact public repositories in `assets/project-repositories.json` | Daily in the same refresh workflow | This remains a separate subset metric. Failed runs leave the last valid bundle untouched. |
| Repository activity | GitHub public REST API for the exact allowlist in `assets/project-repositories.json` | Daily in the same refresh workflow | A failed full collection leaves the last valid bundle untouched and exposes its age through the badge and data-through date. |
| Campaign charts | Approved, versioned campaign registry | Only when a new run is approved | No chart is generated when the registry is empty. Prior approved runs are preserved. |
| Product screenshots | Real application at a reviewed revision | After a material UI change | Keep the prior capture labelled with its source revision until a replacement is reviewed. |

The live workflow publishes to `portfolio-assets`, not to application source. Generation uses `contents:read`; the separate publisher job uses `contents:write` and receives only the validated artifact. The workflow never runs for pull requests, never deploys an application and creates no asset commit when the generated manifest and pointer are unchanged. Its last successful run is recorded in Actions history.

The activity dashboard generates desktop and narrow-screen SVGs from the same validated project snapshot, with matching light and dark variants. Its README selects the narrow version at widths up to 480 pixels. Keep all four assets in the same content-addressed bundle; the linked Markdown report remains the detailed, mobile-accessible alternative.

## Safe refresh procedure

1. Review the exact repository allowlist and verify each repository remains public and relevant.
2. Run the generator and publisher tests before collecting data.
3. Let the default-branch workflow collect public GraphQL and REST data. Its generation job uses a `contents:read` token and verifies repository visibility before collecting project details.
4. Check the workflow run, source-through dates, public-data provenance, project statuses, campaign hashes, images and accessible alternatives.
5. Compare the generated manifest and pointer with the current asset branch. The publisher creates no commit when all generated bytes are unchanged.
6. If a refresh fails, leave the previous assets in place. Inspect the run, fix the source or validator, then use `workflow_dispatch` on the default branch.

## Failure recovery

- **API or schema failure:** keep the previous published assets untouched. Inspect the failed Actions run, check the source response and validator, then re-run the preview after correcting the cause.
- **GitHub REST rate limit:** stop repeated requests. Follow the `Retry-After` or `X-RateLimit-Reset` response guidance and retry only after the indicated wait. If neither header is present, wait at least one minute before a retry; use increasing delays after repeated secondary-limit responses.
- **Invalid or incomplete calendar:** do not render the new calendar. Check the exact repository allowlist, author association, date window, pagination and duplicate commit identifiers before trying again.
- **Project API failure:** reject the entire new snapshot rather than publishing a partially refreshed dashboard. Confirm the exact repository slug and API endpoint.
- **Campaign hash or approval failure:** do not edit an accepted historical result. Add a reviewed correction record that references the original run.
- **Stale published graphic:** use the visible source-through date. If it is more than 36 hours old, mark it stale or remove it from the README until a complete refresh succeeds.
- **Screenshot drift:** capture the actual product only after a material interface change, review its contents for personal or test data, record the immutable source revision and update its README link.

## Change controls

- Keep the allowlist exact; never replace it with account-wide repository enumeration.
- Do not infer accepted milestones or project maturity from commit dates or open pull requests.
- Do not copy historical contribution data whose public/private scope is uncertain.
- Do not add credentials, personal access tokens, third-party paid APIs or app deployment triggers.
- Review workflow permissions, pinned action revisions, diffs, links and asset provenance before requesting publication.
